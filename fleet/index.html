Agent orchestration walkthrough

How the repository coordinates an unattended multi-vendor agent fleet

Written taskings enter isolated git worktrees. Build lanes implement the work, reviewer lanes using a different model provider judge those branches, deterministic checks decide whether the pull request is eligible, and a narrowly scoped merge executor performs the merge. Gitea holds the live pull-request facts; repository files and local ledgers preserve the rest of the operating record.

The Fleet is live in AutomationLab and deliberately exploratory. Its lane mix and dispatch controls continue to change as failures expose weak assumptions, particularly around starvation recovery and an external watcher. A worker can still re-read its assignment, repository policy, operator ruling, review, test result, and pull-request state without relying on a model to remember a conversation.

Built from the orchestration charter, cycle prompt, tasking templates, launcher implementations, run ledger, fleet site specification, usage collector, merge gates, and dated dispatch incidents.

The durable record does the coordinating

A browser chat can carry a lot of context, but it is a weak place to store the state of an unattended delivery system. The next process cannot reliably inspect an earlier conversation, and a reviewer cannot diff a remembered instruction.

The fleet writes the work down. A tasking names one objective, relevant files, boundaries, evidence, and stop conditions. The worker changes one branch in one worktree. Its pull request becomes the durable completion signal. Reviewers leave verdicts on that pull request, CI attaches results to its commit, and the merge executor reads the current state immediately before acting.

The models handle work that benefits from code reading and judgment. Small scripts handle facts that should not vary by model: whether dispatch is paused, whether a PID is live, whether a pull request already exists, whether the branch is current, whether CI passed, and whether the reviewer is authorized to merge.

Each store answers one kind of question

Tasking files
Describe the assignment and authority. A worker receives one tasking rather than a broad standing instruction to improve the repository.
Git worktrees
Give each lane a separate checkout and branch. Concurrent workers do not edit the same working directory.
Gitea pull requests
Provide live branch, review, CI, conflict, and merge facts. The existence of the work pull request is the tasking-consumption signal.
Run ledger
Records launches, exits, blocked decisions, and reasons. A quiet lane has a dated explanation rather than an empty log directory.
PID locks
Prevent a scheduler tick from starting a second process in an occupied lane. Dead PID state can be distinguished from a running worker.
Operator queue and rulings
Hold decisions that require authority or judgment outside the agents. A later cycle can read the answer from the repository.

One worker receives one assignment and then exits

The browser and headless paths use the same underlying command-line model clients. The input mechanism changes. A scheduler pipes a tasking file to the client, sets the worker inside its assigned worktree, and captures the process result.

The worker lifecycle

  1. A cycle writes or selects an eligible tasking. The tasking is lane-specific and names the repository state the worker should inspect.
  2. The spawner evaluates local and remote gates. It checks the pause file, daily cap, newest eligible tasking, live PID lock, available worktree slot, and whether Gitea already has the tasking’s pull request.
  3. The launcher creates or reuses an isolated worktree. The worker receives a branch and directory that no other lane is allowed to edit.
  4. The model performs one bounded turn of work. It reads repository instructions, changes the files in scope, runs relevant tests, and records any unresolved boundary.
  5. The worker pushes and opens a pull request. The pull request body carries the result and evidence. That live object marks the tasking consumed.
  6. The worker process exits. Review and merge are different lanes with different authority. A build worker does not wait around as its own reviewer.

The launcher can start a worker or decline. It does not assign itself new work, widen a task, or interpret a missing pull request as permission when Gitea cannot answer.

The fleet has three timing loops

The old explanation centered on one large cycle. The current design separates capacity pickup from deeper tasking review.

ClockPurposeWhat it does when there is no eligible work
Ten-minute spawner ticksWindows and Linux hosts check their worker lanes and start one eligible tasking.Record the blocking reason and exit without invoking a model.
Forty-five-minute pickup guardNotice new merge, review, ruling, or backlog signals without running a full tasking cycle on every event.Respect the cooldown and leave the existing deep-cycle schedule in place.
Four-hour deep cycleReview the board and operator queues even during a quiet period.Write no new tasking when the current work and limits do not justify one.

The clocks intentionally overlap. The ten-minute tick fills available capacity. The pickup guard reacts to recent change without thrashing. The four-hour cycle prevents a missed event from leaving work untouched indefinitely.

PAUSE behavior. The pause control stops new dispatch and merge execution. It does not claim to terminate a model process that is already running. That boundary is written because “pause the fleet” and “kill every process” are different operations.

The authoring model does not review its own branch

Codex and Claude can both fill authoring or reviewer lanes. A branch crosses to the other provider for judgment, so the control boundary stays the same when the active lane mix changes.

Reviewer credentials remain outside the Fleet AppRole while the review path is being proven, so an authoring lane cannot approve its own work.

The reviewer starts from the tasking, then reads the diff, test evidence, repository instructions, and current pull-request state. It leaves one verdict with actionable findings or approval. The reviewer does not silently edit the author’s branch.

Judgment and policy are separate

A model reviewer can notice that a change satisfies tests while missing the task intent, or that a failure path is unhandled even though syntax is valid. Scripts are better at checking exact state: required checks, latest commit, unresolved conflicts, allowed paths, review freshness, and whether another merge happened since the verdict.

The merge executor requires both. Approval without green policy cannot merge. Green CI without the required independent verdict cannot merge.

The merge path rereads live state at action time

  1. Find the review target from Gitea. The reviewer does not rely on a stale queue copy for branch or commit state.
  2. Read the tasking and repository rules. Scope and authority come from written sources that can be inspected with the diff.
  3. Produce one review verdict. Findings name the file, behavior, and required correction. Approval belongs to the reviewed commit.
  4. Run deterministic eligibility checks. CI must be green, the branch must be mergeable and current enough for policy, the verdict must match the head commit, and required authorities must be present.
  5. Execute the merge through the narrow path. The build lane has no direct merge authority. The merge action is recorded on the pull request and in the orchestration state.
  6. Let the next cycle observe the result. Follow-up work becomes a new tasking or operator item rather than an invisible continuation after merge.

This action-time read is important because review can take longer than build. A branch that was clean when the reviewer started may conflict or receive a new commit before merge.

Subscription capacity is scheduled like worker capacity

The unattended lanes use subscription-backed model providers. An hourly collector reads remaining capacity and reset time through the same runtime identity used by the workers. Prometheus stores provider and window percentages, and dispatch can preserve a reserve for interactive work.

When a provider call fails, the collector retains the last successful reading with staleness visible. A missing or stale capacity value does not become unlimited permission to launch. Before publication, two recording rules remove every source label except provider and window. Account identifiers, credentials, exporter health, host identity, annotations, variables, internal links, and free-form queries remain private.

A scanner-loader defect went through both vendors

A pre-write secret scanner loaded allowlist entries from a TOML configuration file using a regular expression. The file contained eight suppressions, but only three were loaded. A bracket inside one pattern ended the non-greedy match early.

  1. Claude flagged the loader assumption. The first pass identified regex parsing of structured configuration as suspicious.
  2. Codex confirmed the concrete failure. It reproduced the early termination and counted the missing entries.
  3. Claude replaced the regex with a TOML parser. Valid configuration began loading as structured data.
  4. Codex found a failure-path gap. Not every malformed or wrong-typed configuration case failed safely.
  5. Claude corrected the parser boundary. Absent, unreadable, garbled, and wrong-typed configuration now produces an empty allowlist, while valid entries survive beside invalid ones.

The useful result was not vendor symmetry for its own sake. The author and reviewer found different classes of defect in the same control, and the final behavior was pinned by tests.

Failure lessons that changed dispatch

Duplicate pull requests exposed a weak consumption marker

A footer marker was the original signal that a tasking had been consumed. Review latency hid that marker long enough for the spawner to select the same work again. Gitea pull-request existence now supplies the consumption fact, and one tasking can spawn once.

2026-08-12: a future timestamp starved valid work

A future-stamped cycle sorted ahead of the real newest taskings. Both spawners repeatedly chose the already-consumed file, hit the one-spawn cap, and skipped the lane. A later timestamp eventually overtook it. The incident created the next-unconsumed fallback design and the need for a loud starvation signal.

2026-08-04: repository DNS failure stopped dispatch

Scheduled cycles woke, failed to resolve the internal Git service, confirmed that public DNS still worked, recorded the dependency failure, and declined to launch against repository state they could not verify. The ledger shows a stopped fleet with a reason rather than workers guessing from stale local state.

The public Fleet route once looped

A redirect between the Fleet and its legacy alias caused a browser loop. The canonical route now resolves directly at /fleet/, while the old path is kept as a compatibility route.

If I were recreating this from scratch

  1. Write the authority model first. Separate who may task, build, review, merge, and make operator decisions.
  2. Make the tasking a durable file. Include scope, evidence, stop conditions, and the expected output object.
  3. Give each worker an isolated worktree. Do not share one checkout among simultaneous model processes.
  4. Use live pull-request state for remote facts. Consumption, current head, review, CI, conflict, and merge state belong to Gitea.
  5. Keep local process facts local. PID locks, worktree slots, and launcher ledgers should not be inferred from the pull request.
  6. Cross the reviewer boundary. A different model vendor should judge the branch, and scripts should enforce exact policy facts.
  7. Test starvation and stale-state cases. Future timestamps, DNS loss, slow review, duplicate dispatch, and an already-running worker need explicit outcomes.
