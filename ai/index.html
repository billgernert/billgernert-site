How models fit inside the platform without owning it

Models build and review repository changes, correlate overnight operational evidence, classify scanner output, enrich incidents, and help produce reports. They run behind the same identities, budgets, tests, logs, and approval boundaries as other automation. A model can propose work or open a pull request. It cannot grant itself access, suppress a failed gate, or treat missing evidence as permission.

There are two execution paths. Subscription-backed command-line agents handle repository work in isolated lanes. Operational pipelines send bounded inference requests through a gateway that can choose a private local model or an approved external provider. Measured provider capacity controls dispatch, and a failed usage collector closes the gate.

Built from the unattended fleet, AIOps collector and triage pipeline, LiteLLM gateway, subscription-usage exporter, scanner disposition policy, incident analyst, job-reporting project, and dated silence postmortem.

The model receives a job, not general authority

I use models for work that benefits from reading a large amount of context and making a bounded judgment. That includes reviewing a code change against a tasking, grouping several alerts that share a cause, explaining an unfamiliar failure, or ranking a record against written criteria.

The surrounding pipeline handles collection, identity, secrets, budgets, retries, storage, and the final action. This keeps model output in the part of the system where uncertainty is expected. A deterministic check still decides whether CI passed, whether the requested files were in scope, whether a provider has capacity, whether a scanner ran, and whether an operator approved a remediation.

The result is visible in ordinary engineering objects. Build work becomes a pull request. Morning triage becomes a dated digest and finding records. Scanner classification stays attached to the original scanner finding. Incident analysis appears beside the alert it explains.

Two model paths serve different kinds of work

Repository agents

Codex and Claude command-line clients run in isolated worktrees under written taskings. Subscription usage is measured as worker capacity. Branch protection, CI, cross-vendor review, and merge authority govern the result.

Operational inference

Collectors and application code send a bounded request through LiteLLM, a gateway that presents one API surface and applies routing, key, and budget policy to approved models.

The two paths are not interchangeable. Subscription login for a command-line coding agent is not an API credential for an in-cluster service. The gateway manages API consumers; the fleet launcher manages CLI sessions and their subscription windows.

Repository work follows the same delivery path as any contributor

A tasking names the objective, scope, evidence, and stop conditions. A launcher places the worker in an isolated git worktree. The worker reads repository instructions, edits its branch, runs tests, pushes, opens a pull request, and exits.

The other model vendor reviews the branch. That reviewer can understand task intent and failure behavior that a linter cannot. Deterministic merge gates still verify current CI, conflicts, branch head, allowed files, verdict freshness, and merge authority.

This separation matters more than the model names. A model does not review its own branch, and a reviewer does not acquire direct write access to make its finding disappear. The pull request preserves both sides of the exchange.

Why the tasking is part of the control

An open-ended prompt such as “improve monitoring” gives a model permission to choose both the problem and the solution. A tasking identifies the registered defect, relevant files, expected evidence, and the point where the worker must stop for operator authority. That lets the reviewer evaluate the branch against something more precise than whether the change looks reasonable.

Morning triage narrows the evidence before a model sees it

The AIOps path starts with collectors. Monitoring, CI, backup, and delivery systems produce structured records with source timestamps and status. Code normalizes those records, applies known-noise dispositions, checks freshness, and groups exact relationships that do not require a model.

The model receives the remaining ambiguous bundle. It can summarize likely relationships, identify missing context, and draft an actionable finding. The digest keeps separate categories for actionable work, needs information, and known noise. The source records remain available for each claim.

  1. Collectors read each source. They write timestamped records and completion state. A failed collector does not produce an empty healthy input.
  2. Code normalizes and correlates known cases. Stable identifiers, time windows, duplicate suppression, and approved dispositions run before inference.
  3. The gateway receives a bounded bundle. Secret values and unsafe free-form fields are removed. Source text is treated as data.
  4. The model returns a constrained structure. Findings name their evidence, disposition, severity, and missing information.
  5. The pipeline validates and stores the result. Malformed output fails. Valid findings enter the digest and tracking path.
  6. The delivery monitor expects the report. The dead-man switch alerts when the daily digest or its checker goes silent.

The incident analyst uses the same shape at a smaller scale. It summarizes the evidence attached to one failure so the first response starts with context. It does not change the alert or perform the repair.

Scanner triage cannot turn a broken scan green

Secret, container, and infrastructure scanners find candidate problems. A local model can classify a result against the deployed context and reduce noise where the policy allows. The model is downstream of the scanner.

If the scanner did not run, the input is incomplete, or the model response is missing or malformed, the original finding keeps its severity. The model cannot invent a clean scan. Secret values are removed before the request, and the model receives the finding text inside a delimiter that marks it as untrusted data.

Routing considers privacy, task shape, and current capacity

A local open-weight model handles frequent classification and summarization that should remain inside the network. Approved external models handle repository-scale reasoning or a harder inference request when their path and budget permit it.

LiteLLM gives operational API consumers one gateway. It authenticates each consumer with a separate virtual key, applies a per-consumer budget and global ceiling, routes to the configured provider, and exports spend and failure metrics. The virtual keys themselves follow the credential-rotation system.

The unattended repository fleet uses a separate subscription selector. An hourly collector measures remaining five-hour and weekly capacity and records reset times. Dispatch compares actual remaining capacity with the pace needed to reach reset and with an operator reserve. Stale collection is visible and cannot authorize a new worker.

Capacity rule. A provider may be healthy and still be unavailable for new unattended work because the remaining quota is reserved for interactive use or the usage reading is stale. Provider health and dispatch permission are separate states.

What broke

The morning triage went silent for 19 days

The absence was eventually detected from missing run evidence, not from a digest that reported its own failure. The collector and freshness path was repaired and the dead-man control was expanded. The Jenkins-side cause of the original silence was never established, so this page does not assign one.

A model-generated scanner fix still needed another reviewer

The TOML allowlist parser defect was identified and replaced, but the first correction did not safely handle every malformed configuration case. Cross-vendor review found the failure-path gap and produced tests for absent, unreadable, garbled, and wrong-typed input.

Usage data can outlive the collector that produced it

Retaining the last successful reading is useful during a transient provider error, but it can also look current if age is hidden. The collector exports freshness and dispatch refuses stale capacity.

If I were recreating this from scratch

  1. Choose one bounded decision. Start with classification, summarization, or code review where the input and output can be checked.
  2. Build deterministic collection first. The model should not be responsible for discovering whether its evidence exists.
  3. Define the identity and data boundary. Decide which Vault role, provider key, network path, and fields the request requires.
  4. Validate the output before using it. Use a schema and keep the source evidence beside the model result.
  5. Put action in a separate process. A recommendation, pull request, or disposition should cross a policy or operator gate before mutation.
  6. Measure provider capacity and freshness. Missing budget or stale quota must stop new discretionary work.
  7. Add a dead-man signal. A silent collector or digest should become a named monitoring failure.
