Unattended engineering

Multiple builder providers, one unattended control and policy plane

An orchestrator reads the queue and durable Gitea state, then dispatches one eligible task through a provider adapter. Claude Code, Codex, Grok, and Gemini are approved builders using the same launch, result, and failure contract. A provider can change without changing task eligibility, worktree isolation, review gates, merge policy, or durable state.

The scheduler decides whether a provider is called

Ten-minute spawner ticks check PAUSE, the daily launch cap, the newest tasking, live PID locks, and whether that tasking has already run. An idle tick exits in under a second and calls no model.

A pickup guard handles new work after its cooldown. The four-hour cycle still performs a full board review when the lab has been quiet.

Provider adapters give the orchestrator the same launch, result, and failure interface for Claude Code, Codex, Grok, and Gemini. Task policy selects an approved builder. The adapter can execute a task; it cannot decide whether the task was eligible or whether its pull request may merge.

The operator interface can observe the fleet, pause dispatch, or request a cycle through chat, but it is not the scheduler and holds no unique state. Gitea records the task, branch, pull request, CI result, reviewer verdict, and merge outcome. Routine low-risk work can merge after its deterministic gates. Work outside that policy waits for manual approval.

Failure that changed the design

The old consumption marker created duplicate pull requests

A worker originally marked its tasking as consumed by appending a footer on its own branch. Review latency kept that footer away from the spawner, so completed work still looked new and launched again. Six duplicate pull requests arrived in pairs. A tasking can now launch once, and the existence of its Gitea pull request is the consumption signal.

Certificate and secret lifecycle

Renewal, deployment, and verification run before expiry

Internal services, Windows and Linux hosts, and Kubernetes workloads use different issuance paths, so the automation meets each system where it runs. Jenkins coordinates the server-side jobs, Vault supplies credentials at run time, AD CS issues internal certificates, and cert-manager handles the Let's Encrypt wildcard through DNS-01.

Watch

Inventory and expiry data identify certificates entering the renewal window.

Issue

AD CS signs internal requests. cert-manager completes DNS-01 for the wildcard.

Deploy

Ansible installs server certificates. Kubernetes updates its managed secrets.

Verify

The job checks the presented certificate, chain, name, and new expiration date.

Record

Grafana shows the next expiry, last rotation, and any failed deployment.

Certificates

Zabbix hosts receive rotating internal certificates, internal web endpoints use the managed wildcard where that trust model fits, and private services use the internal authority. A failed validation leaves the working certificate in place and raises an alert.

Secrets

Rotation jobs write the new credential to Vault, update the consuming service, verify the new value, and retire the old one after the consumer succeeds. The job stops before removal when it cannot verify the replacement.

Server provisioning

One request builds the same server across every system that needs to know it

A basic Windows or Linux build finishes in about five to ten minutes. The request still passes an approval gate, and each platform keeps ownership of its own part of the result.

Ownership during a basic server build
Request and gate Jenkins validates the request, runs the collision check across the authoritative systems, presents the plan, and keeps the execution log.
Infrastructure NetBox allocates the address. Terraform manages the requested definition, plan, apply, and per-VM state. The Proxmox provider sends the approved change to the cluster.
Configuration Ansible configures the operating system. Windows uses a template rebuilt from code and can join the domain, add features, install selected software, and enroll in MFA. Linux starts from a cloud image and follows its own role path.
Registration Vault receives the host's monitoring key, Zabbix receives the host, DNS receives the record, and the pipeline records the completed machine in git.
Partial failure Before apply, the pipeline releases reserved resources. After apply, it keeps the VM and resumes forward on the next run, so a live machine is not removed underneath a failed configuration step.

Recovery testing

The backup check includes booting the restored service

97s destroy to initialized and unsealed

The recovery pipeline restores critical VMs into an isolated test path every week, boots them, checks the application, and removes the test copy. In the measured Vault run, the VM was destroyed outright and restored from that night's snapshot. A canary secret written minutes before the destroy survived, and credential fetches worked after the service returned.

The first implementation needed twelve reruns. Several checks could report success before they had verified the restored service. Those checks now test the service response and the canary value before the run is allowed to pass.

Experience behind the lab

I built AutomationLab from work I had already learned to operate at scale

My background is Windows-heavy infrastructure, virtualization, identity, monitoring, and automation across higher education and county government. The lab gave me a greenfield place to connect those systems through Kubernetes, infrastructure as code, GitOps, and newer AI tooling.

Automation and operations

I grew a Jenkins platform from 20 scripts to 135 Python and PowerShell jobs. A PowerShell service I wrote watched 350 virtual desktops, patched their images and fixed the common failures without an operator, so we never had to buy the $30,000 a year product that did the same job.

Infrastructure at scale

I operated a 1,000-VM VMware estate and supported an environment with roughly 400 servers and 15,000 workstations. I recovered about $10,000 per month in missed billing, supported a two-site Horizon environment using Cloud Pod Architecture, and automated patching for Horizon desktop images.
