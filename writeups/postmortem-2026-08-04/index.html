Incident

The node that took the platform with it

On 2026-08-04 one node in a five-node Proxmox cluster stopped answering, and it took routing, internal DNS, the git server and the control plane down with it. I was hundreds of miles away with no way in. This page is the account: the timeline as the logs recorded it, what survived, what failed, and what changes. Two sections cannot honestly be written yet, so they say so instead of guessing.

Timeline

All times are UTC on 2026-08-04 unless another date is given. They come from three sources that survived because none of them lives on the failed node: the WireGuard handshake log on my laptop, the agent fleet's append-only run ledger in the repository, and Cloudflare's own error pages. The ledger is a committed file, so the timestamps below are copied out of it rather than remembered.

  • 18:35:15 The agent fleet's scheduled cycle finishes normally and dispatches four worker sessions. That detail matters later.
  • 19:16:46 The last WireGuard keepalive that my laptop and the lab's firewall both agree on.
  • 19:17:15 The first WireGuard timeout. This is the start of the outage, and the gap between these two lines is the whole of what the evidence can say about the moment of failure.
  • From about 19:20 Every hostname behind the Cloudflare Tunnel returns error 1033, which is Cloudflare saying the tunnel connector on the far end is gone. Internal addresses time out. The firewall's own console is unreachable.
  • 20:02 to 20:04 A manually started fleet cycle cannot resolve the git server and stops without dispatching anything.
  • 00:02 on 08-05 The next scheduled cycle runs. It fails DNS three times, checks public DNS and finds it healthy (so the internet is fine and the lab is not), refuses to dispatch work against a repository state it cannot confirm, writes one line in its ledger, and exits. Every scheduled cycle for the rest of the outage repeats that refusal.
  • 2026-08-05 onward The lab stays down. I am away from the hardware with no out-of-band path to it. Work continues against an offline copy of the repository, which turned out to be a story of its own.
  • 2026-08-08 This page is written. The lab is still down and nobody has touched the hardware yet, which is why two sections below are unfinished rather than filled in.

Impact

The failed node was carrying four things at once: the firewall running OPNsense, which is all routing and the VPN; one of the two Active Directory domain controllers, which is internal name resolution; the Gitea server, which holds the repository every pipeline and every agent reads; and the Ansible control host. Losing one node removed routing, name resolution, source control and the control plane in a single stroke.

High availability did not help, and the reason is the whole lesson of the incident. Proxmox HA restarts a guest elsewhere in the cluster when the node it was running on fails, and it can only do that over a network. The network was one of the guests on the node that died. The mechanism meant to rescue the guests was itself one of them.

Nothing a reader of this site would notice was lost. The public site is served by Cloudflare Pages from a mirror repository and has no runtime dependency on the lab, so it stayed up for the entire outage, checked from outside the failed network. That was not luck. It is the reason the site is built that way, and this is the first time the design has been under real load.

No data loss has been observed so far, and "so far" is doing real work in that sentence. Backup integrity, database state, and whether the four dispatched worker sessions left uncommitted work behind are all things I can only confirm once the hardware is back.

What worked

Two designs were on trial, and both were written down before they were tested.

The site does not depend on the lab. Cloudflare Pages serves the site from a mirror repository that the platform pushes to, so no machine in the lab is in the path of a visitor. The portfolio survived its own platform's worst day, which is the entire point of splitting them.

The agent fleet refused to act blind. Every four hours the scheduled cycle woke up, tried to confirm the state of the world, could not reach the repository, and declined to dispatch anything. Each time it wrote a fully explained refusal into the ledger, and it made zero blind dispatches for the whole outage. An estate that stops cleanly when it cannot see is the property the rest of this site is trying to earn, and the dispatch half of it passed its first real test.

The honest asterisk The refusal discipline held. Some of the machinery around it did not. The same week's reviews found commit hooks that failed open rather than closed, and a ledger that could not push its own lines. Both became fixes. "The fleet declined correctly" and "every guard around the fleet was sound" are different claims, and only the first one is proven here.

The outage also handed the fleet something strange: several days of a frozen, perfectly stable copy of the repository, with nothing merging under anyone's feet. It became the most productive review and build window the platform has had. The outage cost the lab days of uptime and paid back weeks of engineering, which is a trade I did not choose and would not repeat.

What failed

Three designs failed. Each is written below in the shape the lab uses for any failure mode: what it looked like, what it actually was, how you get out of it, and what stops it happening again. Where a recovery step has not been walked yet, it says so rather than implying it has.

Placement: one node held the front door

  • Symptoms. A single node stopped answering and four unrelated services went with it. Cluster HA, which exists precisely for a node loss, did nothing.
  • Diagnosis. Routing, one domain controller, the repository and the control host had all been placed on the same node. The concentration was known and had never been examined. HA cannot move a guest across a network the dead node was providing.
  • Recovery. There is none that does not involve standing in the room, which is failure two. Once routing is back, HA settles on its own.
  • Prevention. A placement rule, written as an acceptance criterion so it can be tested rather than admired: no single node's loss may remove routing, repository, DNS and control at the same time.

Reach: there was no out-of-band path

  • Symptoms. Nothing to try. No console, no way to power-cycle a node, no way to confirm what was broken without being physically present.
  • Diagnosis. Every path I had into the lab ran through the lab. The VPN terminated on the failed node, the management interfaces sat behind it, and the tunnel connector needed the routing that had just gone away.
  • Recovery. Travel to the hardware. That is the honest answer, and it is why this outage is measured in days rather than minutes.
  • Prevention. Console access that survives the network being gone, and a heartbeat out to an external service so silence pages me instead of waiting to be noticed. Both are designed and neither is built, so neither is claimed here as working.

Sight: the monitoring was inside the blast radius, and so was my browser

  • Symptoms. No alert fired. From outside, a dead estate and a quiet estate look identical. On top of that, my own laptop reported the public site as down while it was up for everybody else.
  • Diagnosis. Two versions of the same mistake. The monitoring runs inside the estate it monitors, so when the estate died the monitoring died before it could say anything. And my laptop resolved the public domain through the lab's internal DNS, so with the lab gone the name did not resolve at all and the browser drew the obvious wrong conclusion.
  • Recovery. Check from a network that owes the lab nothing before believing what your own machine tells you. A phone on mobile data settled the question in seconds, once I thought to ask it.
  • Prevention. A watcher that shares no fate with the lab, and resolver settings on my own devices that fall back to public DNS when the lab path is dead, so a dead lab can never again impersonate a dead internet from my own chair.

Root cause

This section completes after recovery, per the house rule

The honest answer today is that I do not know. The node stopped answering on every interface inside a 29 second window, between 19:16:46 and 19:17:15. A hardware failure, a power event and an operating system panic are all consistent with the evidence available from outside the building, and nothing available from outside the building can tell them apart. Guessing further would be writing fiction, so this section waits for the hardware.

Recovery

The order below was written during the outage and has not been walked. Under the rule this whole site runs on, that makes it a plan and not a procedure, and it stays labelled as one until the day it is executed.

  1. Reach the failed node's console and diagnose before touching anything. The evidence dies the moment the machine is power-cycled.
  2. Routing first. Nothing else can be reached until the firewall is back.
  3. Name resolution next. The second domain controller lives on a different node and should have survived, so verify that rather than assume it. Internal DNS has to be sound before any service that depends on it comes up.
  4. Let cluster HA settle, then verify quorum and storage instead of trusting that they settled.
  5. The git server and the tunnel last, once the platform underneath them is confirmed sane.
  6. Check my own workstation's VPN client and resolver before trusting a single thing it reports, because it already lied once during this incident.

Action items

Each of these is tracked as a work item in the backlog, and this page will link the records as they close. None of them is described here as done, because none of them is.

  1. Placement review, then a live-fire drill. Check the estate against the acceptance criterion above, then take the same node down deliberately, with me standing next to it, and prove the criterion holds. A failure mode you have only met by accident is not one you understand.
  2. An out-of-band dead-man switch that shares no fate with the lab. The lab heartbeats out to an external service and silence pages me. The design is chosen. It is not built, and this page will not claim it works until it has fired in a drill or in anger.
  3. Resolver settings that fail open to public DNS on my own devices when the lab path is dead.
  4. Console access that survives the network being gone.

The one-sentence version

The platform's first total outage proved the two designs I most needed to be true, the site's independence from the lab and the fleet's refusal to act on what it cannot verify, and it exposed the one assumption I had never written down: that the node holding the front door would not be the one to die.
