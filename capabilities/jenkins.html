Jenkins: delivery and recovery

How I modernized AutomationLab's delivery platform, rebuilt its production controller, recovered its history and workers, and turned the gaps into recovery checks.

Why I rebuilt the delivery platform

I use Jenkins to run the work behind AutomationLab: infrastructure changes, image builds, repository checks, monitoring maintenance, backups, and publication of this website. Those workflows made the controller useful. This modernization project addressed a harder question: could I replace the controller and still trust the delivery system around it?

The work covered separate development and production controllers, pull request validation, test reports, image promotion, concurrency controls, delivery measurements, and recovery. I tested the recovery path by deleting the production controller and its storage during an approved maintenance window.

That exercise produced a measured controller rebuild and exposed missing pieces. Authentication, automatic triggers, history, and permanent agents each needed their own recovery path. The resulting design checks those dependencies explicitly: a running Jenkins page is only one part of a working delivery platform.

Two controllers, one configuration base

Development and production run as separate Jenkins controllers with separate storage. They share a configuration base, with deliberate overrides for the differences between environments. Jenkins Configuration as Code defines controller settings, and Job DSL defines jobs, descriptions, parameters, and schedules. Pipeline code and credential references live in Git; secret values remain in external stores.

The development controller provides a place to exercise configuration and plugin changes before production. Its seed follows the development branch; the production seed follows protected main. Promotion uses a reviewed pull request between those branches. Separate webhook configuration directs changes to the appropriate controller.

Separation also applies to authority. Development has a different Vault role that denies production credentials for destructive operations. Pipeline guards make relevant infrastructure operations plan-only or skip them on development. Scheduled production work is suppressed there so the second controller does not duplicate backups or maintenance.

Workers suited to the workload

The controllers coordinate work. Kubernetes supplies short-lived workers for supported pipeline labels, including provisioning and Python workloads. Each build receives its own pod and workspace, and the worker disappears when the build finishes.

Three retained virtual-machine agents complement those pods: one Linux worker and two Windows workers. They support workloads that need those operating systems and installed tools. Their lifecycle differs from the Kubernetes workers, so their recovery requirements differ too.

During the rebuild, Kubernetes could create workers, but the three permanent node definitions had existed only in Jenkins. Deleting the controller storage removed those definitions while leaving the worker machines behind.

On September 6, 2026, I restored all three connections using WebSocket and updated their connection secrets one worker at a time. All three returned online, and the five queued Windows builds drained from the queue. The recovery configuration now declares the node definitions and records the reconnection procedure alongside the controller recovery steps.

Pull requests test the proposed merge

Gitea Actions checks secrets, image vulnerabilities, configuration, and repository tests. Jenkins adds a merge-preview check: it verifies the requested pull request commit, combines it with the reviewed target branch, and runs the offline suite against that proposed result. A conflicting merge or a changed head fails before tests run.

The dispatcher and runner load their pipeline definitions from protected main. A pull request cannot replace the privileged pipeline that schedules it or reports its result. The stage executing pull request content receives repository-read credentials, but no status-writing token or Vault role. Status publication happens in separate workers that have not checked out pull request content.

The suite produces JUnit XML. Jenkins publishes individual test results and archives the report with a fingerprint, so a failed build can identify the failing test instead of offering only a console exit code. The final result is attached to the exact pull request commit as the required jenkins/pr-ci status.

Job DSL creates the runner's parameters before its first build. A fresh controller should accept a valid request immediately, without a deliberately failing run to establish its parameters.

Concurrency with an explicit limit

The first PR runner allowed a backlog to form because it serialized independent builds. The dispatcher now reserves at most four active PR heads across the repository. Only one dispatcher run reserves work at a time, while isolated runners execute concurrently.

Fresh pending reservations occupy capacity, preventing each scheduling tick from submitting the same work again. A successful head is not retried, repeated failures stop further automatic attempts for that head, and runner timeouts limit how long work can remain active. Independent PRs can progress together while the controller has a defined limit on the work it launches.

Promote the image that was tested

The provisioner worker image is promoted using an immutable digest. The image is built, its digest is recorded, and the signed artifact is verified before that same digest is placed in the agent configuration. Repository checks require the digest record and configured worker image to agree.

A tag can point to different content over time; a digest identifies the artifact that passed promotion. Rollback selects a previously recorded, verified digest and reapplies the configuration without rebuilding an image during an incident. This is a working promotion path for the provisioner, not a claim that every image has completed the same adoption.

Measurements with defined meanings

A read-only exporter gathers Jenkins API data for Prometheus. Grafana presents build reliability, queue depth, oldest queued wait, duration, and executor capacity. The exporter has its own scrape-success signal, so loss of access to Jenkins is visible.

Delivery measurements use an explicit list of production deployment jobs. Test runs and maintenance do not become deployments merely because Jenkins ran them. The implemented DORA measures have specific definitions:

  • Deployment frequency: successful qualifying deliveries completed in the previous 24 hours.
  • Lead time: median elapsed time from recorded source changes to successful delivery completion over seven days.
  • Change failure ratio: failed or unstable qualifying delivery attempts divided by completed attempts over seven days.
  • Recovery time: a qualifying failure through the next successful delivery, using recovered incidents within 30 days.

These measurements depend on retained Jenkins events. Recovery time here is a pipeline-based measure, not an independent observation of customer impact or service availability. If there is no qualifying change timestamp or recovered incident, the exporter leaves the sample absent instead of manufacturing a zero. I do not claim a delivery-performance ranking from these data.

Back up what source cannot recreate

Configuration in Git can rebuild jobs. It cannot recreate their historical console output, build records, or fingerprints. That evidence has its own retained storage, separate from the disposable controller volume.

The backup policy applied on September 6, 2026, schedules a daily UTC job. It reads the Jenkins home through a read-only mount and archives job history and fingerprints, excluding job configuration files. The job cannot overlap itself. It writes a partial archive, validates the archive stream, calculates a SHA-256 checksum, and publishes the completed files by rename. Retention keeps the newest four completed archives.

Recovery first rebuilds the controller and seeds its current jobs from source. History import excludes archived job configuration and verifies that the newly seeded configuration checksums remain unchanged. Historical evidence can return without replacing reviewed definitions with older settings.

The older backup format contained more controller state. Those legacy archives remain sensitive and restricted while the selective policy replaces them through normal retention. The completed history restoration described below used a legacy archive; applying the new schedule is not evidence that a new selective backup has already completed.

Architecture

The four-eyes offboarding pipeline is one example of the controls Jenkins coordinates. It records the requester and requires a different, explicitly authorized approver. Blank or malformed identity stops the run. The workflow disables access first and defers destructive cleanup to a later sweep, preserving a recovery window. The decision and result remain in the build record.

What the destructive exercise proved

On September 2, 2026, I deleted the production controller workload and its controller volume during a declared quiet window. Recovery rebuilt from committed configuration and a pinned chart, then exercised the reconstructed system.

The recorded controller recovery took 6 minutes 55 seconds. It recovered the expected catalog, proved selected schedules, and completed a pipeline on an ephemeral worker. That read-only assurance pipeline reported estate drift, an accepted completed result for this probe.

The exercise verified automation access after the normal Entra authentication configuration returned and confirmed that the exporter could scrape again. New controller and storage creation timestamps established that this was a replacement, not merely a restart.

The measurement has a boundary The 415-second result measures the recorded controller exercise. It does not include all subsequent repairs, history restoration, or recovery of the entire infrastructure estate. The expanded recovery procedure has not yet undergone another complete destructive drill.

A later controlled import recovered 9,814 historical build records from the retained legacy backup while preserving the seeded job configuration. These are dated results from the September exercise, not live counters.

The failures improved the recovery contract

The drill exposed a distinction between preserving a credential outside Jenkins and restoring Jenkins's ability to accept it. The automation API token's external copy survived, but its server-side record had been lost with the controller volume. Recovery now reinstalls that relationship and verifies it again after Entra authentication returns.

The Git notification token had the same hidden dependency. Repository webhooks remained configured, yet Jenkins rejected their deliveries after the rebuild. Manual jobs could still run, which initially obscured the missing automatic path. The corrected procedure restores the notification token from its escrowed record, validates the webhook consumer, and checks Jenkins polling. Successful source-triggered publication and synchronization jobs proved that merges were causing work again.

The exporter needed a restart to reload the recovered credential. The PR runner needed parameters defined during seeding. The missing static agents demonstrated that testing one Kubernetes worker did not prove Windows or retained Linux capacity.

Each finding became a separate recovery check. The procedure also records its bootstrap dependencies: the external secret system must be available, and the credentials needed to reach it must survive outside the controller volume.

Jenkins publishes this account of Jenkins

This website follows the same reviewed delivery path. I edit source in the private repository, merge the reviewed change, and let Jenkins prepare the public publish set. A fail-closed scrub gate checks allowed content for internal addresses, hostnames, credential material, and other prohibited strings before publishing the public mirror. Screenshots require separate human review because a text scanner cannot read an image.

That publication path became part of the recovery evidence. After restoring notification authentication, a repository change again triggered the website sync automatically.

The value of the modernization is visible in these working relationships: reviewed configuration creates the controller, isolated workers validate proposed changes, immutable artifacts carry through promotion, measurements explain what ran, and retained evidence survives a replacement. The drill made the remaining assumptions visible and gave me concrete checks for the next recovery.
