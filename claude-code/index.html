Agent orchestration

How the unattended multi-vendor agent fleet works

This repository is worked by written taskings, isolated git worktrees, cross-vendor review, and small scripts that decide when a worker may start. Today the live build path is Codex-authored work reviewed by Claude lanes, Codex reviewer lanes cover Claude-authored work, and every stage is bounded by Gitea pull-request state, PID locks, `PAUSE`, daily caps, and operator authority. The page below separates what is running, what is manual, what is blocked, and what is still design work.

Why any of this works: the durable record comes first

The interesting part of this page is not that two model vendors are involved. It is that the repository already stores the facts an unattended worker can safely read: taskings, policies, backlog state, generated pages, review verdicts, merge rules, and dated operator rulings. Git preserves the durable record. Gitea adds live pull-request facts that cannot safely wait for merge timing. PID locks and ledgers supply local state for the launchers. The fleet works because the control surface is inspectable rather than conversational.

That distinction matters during disagreement and during failure. A worker can diff a file, re-read a PR, or refuse a merge when a gate is unclear. It does not need to remember a chat, infer a missing rule, or trust that a prior run already told the truth. The scripts stay simple, the models stay scoped, and the operator can audit the boundary between them.

Headless workers are just command-line agents with one written assignment

A browser chat and a headless worker use the same underlying model. The difference is only the transport. In a browser, a person types. In a headless lane, a scheduler pipes one tasking file into the CLI, the process does one round of work in its own git worktree, opens its pull request, and exits.

The commands are ordinary CLI invocations, not pseudocode:

Get-Content tasking.md | claude -p
codex exec "$(cat tasking.md)"

Each worker receives one written tasking, starts noninteractively, works in its own git worktree and branch, opens a pull request, writes its result in the PR body or review body, and exits. The important point is not a perfect CLI symmetry between vendors. It is that both tools accept noninteractive input and can be launched by plain schedulers.

How the fleet wakes up: two spawners, three clocks

The two spawners are intentionally dumb: they start an eligible worker or they exit. The detailed guard list belongs in prose because the semantics matter more than the drawing. `PAUSE` is a dispatch stop, not a process-kill claim. The committed checks stop new launches and merge execution; they do not claim to terminate already-running workers.

Usage is monitored like any other finite fleet resource

The fleet depends on two subscription-backed model providers, so remaining quota is operating capacity. An hourly collector reads each provider's aggregate five-hour and weekly limits using the same runtime identity the workers already use. It exports percentages and reset times to Prometheus, retains the last successful reading if a provider call fails, and alerts privately when collection goes blind.

The public boundary is deliberately smaller. Two recording rules remove every source label except provider and window before this dashboard can query the data. Account identifiers, credentials, exporter health, pod and host identity, annotations, variables, internal links, and free-form queries remain private. The dashboard below is a separate read-only model whose exact panels and query strings are enforced in CI.

Cross-vendor review is the safety boundary, even though the live build path is asymmetric

The current live fleet is not "Claude builds and Codex reviews" anymore. Codex build lanes open work pull requests. Claude reviewer lanes review those Codex-authored branches and execute merges when the gates are satisfied. Codex reviewer lanes are the other half of the same cross-vendor rule: they review Claude-authored pull requests and leave one verdict comment, but Claude build lanes are retired today, so that side of the pattern mostly applies to holdovers and future narrow exceptions rather than to the normal build path.

That is still a multi-vendor fleet. Both vendors participate in judgment. What changed is who authors new work today, not the rule that a vendor should not review its own branch.

Designed next state, not the current merge path

Two improvements already have committed design or code, but they are not both running. Webhook reviewer dispatch is still design work. The deterministic merge executor script ships in the tree, but the hard cross-account reviewer gate is default-off because the dedicated reviewer identities are provisioned yet still blocked from the lane AppRole that needs to fetch them. The page therefore labels this whole picture as the next state, not as the current path.

Review verdicts today are comment-state reviews on /pulls/<N>/reviews, with a VERDICT: APPROVE or VERDICT: BOUNCE line in the body and the judged commit SHA attached to the review object. That is not the same thing as a formal Gitea APPROVED review object from a dedicated reviewer identity. The dedicated reviewer accounts exist, but the lane AppRole still cannot fetch their PATs, so the formal cross-account approval path is blocked and the merge-executor script keeps that gate default-off.

Files are the primary transport, and Gitea supplies the live facts

The system no longer claims that everything is a file, because that would be wrong today. Files are still the primary transport for taskings, rulings, prompts, policy, and generated state. Git preserves that durable record. Gitea pull-request state supplies the facts that cannot safely depend on merge timing: whether a tasking has been consumed, what the current head SHA is, what verdicts are attached to that head, and whether the branch is mergeable.

That is why consumption moved away from tasking footers. A footer on an unmerged branch is invisible to a spawner that only reads main. A pull request existing in Gitea is not. The design point survived the change: the fleet still does not need a live agent-to-agent message bus.

Different ledgers also do different jobs. The merge executor has its own ledger. The tasking cycle has its own run ledger. The spawners write only meaningful actions such as SPAWNED, CAPPED, or DAILYCAP; an idle tick is meant to be silent. Review verdicts are not ledger lines at all. They live on the pull request they judged.

The timing story is three clocks, not one cycle

The old page over-centered one four-hour loop and one stale half-hour helper. The current model is three distinct clocks with three distinct jobs. First, the 10-minute spawner ticks on the Windows and Linux worker hosts start eligible workers or exit without invoking a model. Second, the pickup guard is meant to notice new signals and summon the tasking agent only after a 45-minute cooldown. Third, the deep cycle runs the tasking agent unconditionally every four hours as the quiet-period backstop.

Those clocks do not all have the same maturity. The spawner ticks and the four-hour deep cycle are real running machinery. The pickup-guard script and its cooldown are committed, but that path is mid-change: its watched signals still refer to the retired report-file transport, so this page treats the guard as a blocked transition rather than silently calling it fully current.

What a spawner checks before starting a worker

  1. `PAUSE`. If the fleet pause file is present, new launches stop.
  2. Daily spawn cap. The public write-up and committed references describe a hard daily wall before any more launches are attempted.
  3. Newest tasking per lane. A spawner should consider the newest eligible tasking for that lane rather than replaying older files.
  4. Live PID lock. A live process means the lane is occupied.
  5. One spawn per tasking record. A tasking that already launched once is not re-used.
  6. Concurrency availability. If no lane slot is free, do not start another worker.
  7. Launch. Start the worker in its own git worktree.

The page is careful about scope. The exact 80-spawn cap is named in the source material, but the live spawner scripts themselves are operator-managed outside this repository, so this page does not freeze a broader claim about fleet-wide versus per-host scope that the tree here cannot prove.

The one-spawn rule exists because the old design made duplicate pull requests inevitable. A worker used to mark consumption by appending a footer to its tasking file on its own branch. Review latency hid that footer from the spawner, so the same tasking could be launched again after the work was already done. The fix is the pair now named in the contracts: one spawn per tasking, ever, and Gitea pull-request existence as the consumption signal. A dead lane gets a fresh tasking, not a retry in place.

Liveness is now described in PID-lock terms rather than deadline guesses. A spawner writes the worker PID when it launches. The next tick checks the process table. A live PID keeps the lane occupied. A dead PID means the lock is stale and may be cleared. The retry rule is not "run the same tasking again on the next tick." It is "issue a fresh tasking after the failure is understood."

The merge path separates policy, review, and execution

Operator authority and mechanical merge execution are different things. Bill sets policy, holds consequential work, and remains the authority for anything that raises a real question. Claude review lanes execute routine merges today when the written gates are satisfied. The deterministic merge script is the attempt to take the last mechanical button press out of the model path, but it is not yet the live enforced path.

The merge executor in the repository already reads verdicts from /pulls/<N>/reviews, checks the current head SHA, checks CI, checks mergeable, checks HOLD, checks PAUSE, and defaults to dry-run. What stops the page from calling it live is the identity transition: the cross-account reviewer logins are provisioned, yet the lane AppRole still cannot fetch those reviewer PATs, so the formal reviewer-login gate stays blocked and the live merge timer remains a designed cutover rather than a running one.

The operator queue itself is a running control, not a future mock-up. It is a committed file that the tasking path maintains as the durable list of what still needs Bill. What is not running is a separate queue application, a live webhook-fed control plane, or a claim that evidence-clearing happens without a repository update.

The loop working on a real defect

The mechanism is only interesting if it catches something. One outage-week defect did exactly that. A pre-write hook that scans for secret-shaped strings loaded its allowlist from .gitleaks.toml with a fragile pattern match. The file contained eight suppressions. Only three were being read correctly.

  1. Claude flagged the loader. The first build pass found the pattern-match assumption suspicious.
  2. Codex confirmed the defect. The non-greedy match stopped at the first closing bracket inside a regular expression, so five suppressions were silently missing.
  3. Claude replaced the parser. The allowlist started reading from a real TOML parse rather than from a regex.
  4. Codex found a second defect in the fix. Malformed configuration paths were not all handled safely yet.
  5. Claude fixed that and the review returned approve. Absent, unreadable, garbled, and wrong-typed configuration now fail closed to an empty allowlist, while valid entries still survive beside invalid ones.

The example is one direction of the larger system: Claude produced the fix and Codex reviewed it. Other assignments run in the opposite direction when there is Claude-authored work to judge. The lesson is not that one vendor is intrinsically the builder and the other the reviewer. The lesson is that a model should not grade its own branch.

Failure lessons that changed the fleet

The duplicate-pull-request incident is why the page talks so carefully about consumption. Review latency once hid the old footer-based consumption marker, so a finished tasking could look idle and launch again. The current rule pair, one spawn per tasking and Gitea PR existence as the consumption signal, was written directly out of that failure.

The dispatch-layer outage on August 12, 2026 is why this page does not overclaim about spawner robustness. A future-stamped tasking cycle sorted ahead of the real newest taskings, so both spawners repeatedly selected an already-consumed file, hit their one-spawn cap, and silently skipped the lane. Recovery came only when a later cycle's timestamp finally sorted above the poison value. The fallback-to-next-unconsumed selection and loud starvation signal are filed work, not running safeguards, so this page marks that robustness as blocked rather than pretending the current spawners self-heal.

The August 4, 2026 outage is why this page keeps the dispatch rule separate from the rest of the fleet story. Every scheduled cycle after the outage woke on time, tried to pull the repository, failed to resolve the git server, checked public DNS, concluded the internet was healthy and the lab was not, and declined to dispatch against a repository state it could not confirm. Each run wrote its reason to the ledger and exited cleanly. That ledger is the dated evidence that the fleet stopped rather than guessing.
