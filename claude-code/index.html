Build workflow

The platform builds itself, and here is exactly how

AutomationLab is built by two AI agents from rival vendors. Claude Code writes the code, OpenAI's Codex reviews it, and neither ever grades its own homework. A timer wakes them every four hours, every message between them is a file in git, and a file named PAUSE stops the whole thing. This page explains the machinery plainly, says which parts are running today and which are still designs, and shows the loop working on a real security defect. It starts with why any of it is possible, which is the written record the platform keeps rather than the models it rents.

Why any of this works: the data comes first

An agent is only as good as what it can read, so the interesting part of this page is not the models. It is that the platform writes everything down in places a program can open. Git holds the code, the pipelines and the runbooks. An append-only run ledger holds one line per agent run and is never edited. NetBox holds the hosts, addresses and services as structured inventory. Design decisions are dated files rather than recollections, and every review verdict below is a file too. None of that was built for AI. It was built because an operator forgets. It turns out to be what an agent needs.

What that already buys, and you can check all four. The outage postmortem on this site was written by the fleet from the run ledger and the surviving logs rather than from my memory, and it marks the two sections the evidence cannot support yet. The cross-vendor review chain described below runs on the same material, and one fact-checking pass through it caught fourteen wrong claims across three drafts before a word of them published. The controls the fleet works under were drafted the same way: the merge contract, the operator queue and the session charter were written by agents reading those same files, and every one of them was reviewed by me before it took effect. And this page is its own example, because the week it describes ran while the lab was down and I was working from a phone: 29 work branches and three fact-gated drafts, produced from the repository rather than from a running estate. Those are artifacts, not adjectives.

What the same foundation is designed to buy next, and does not yet: an agent triaging a live incident while it is still happening, an agent working an emergency alongside me, and an agent reviewing an architecture proposal before it gets built. None of the three exists. The proven behaviour today is the opposite one, and it is further down this page: through the whole outage the fleet did not troubleshoot anything, because it could not verify what it would be acting on, so it stopped. Turning that refusal into safe live analysis is roadmap, and nothing here claims it works.

Two agents, two vendors, one repository

An AI agent fleet sounds exotic and is not. The parts have names you already know. Claude runs in a browser tab. Claude Code is the same model as a command-line program. Codex is OpenAI's equivalent command-line agent. A timer runs on a schedule the way any scheduled job does, and a git repository holds plain text files. That is the whole inventory.

Start with the browser tab, because the trick is easier to see there. Claude in a browser is a chat. Give that chat a file tool pointed at the platform's repository and it can write a dated text file into the repo when I say "record that decision". Now take the same model as a command-line program. Like any command-line program, you can feed it text on standard input instead of typing at it. Write the assignment in a file, pipe the file in, and the same intelligence does the work with no window and nobody watching, then exits. That is all a headless agent is: the chat, minus the chat.

Feeding an agent looks like this, and it is real rather than pseudocode:

cat brief.md | claude -p         # "here is your assignment, go"
codex exec "review this branch"  # the rival vendor's agent, same idea

Two vendors is the point, not a hedge. Claude Code builds. Codex reviews, fact-checks and red-teams. A model reviewing its own output shares its own blind spots, so the reviewer is deliberately a different company's model. One fact-checking pass during the outage week caught fourteen wrong claims across three drafts of these very pages before a word of them published.

The stations are offset in time, and that is worth being precise about because it is the part people assume is magic. The cycle is a dispatcher, not a waiter. It acts only on work that is already finished and sitting in files, never on anything in flight. So a branch built this cycle gets its review dispatched the next cycle, and its merge decision the cycle after that. One station per cycle, every lane busy, each lane working a different generation, like any assembly line. A worker finishing is itself a signal, and the cheap half-hour tick that notices signals summons the next full cycle early, so "next cycle" usually means within the half hour rather than four hours later.

Work is files in git

The agents never talk to each other live, and I never talk to them live either. Everything is a memo in the repository. Work to do sits in a taskings folder, one file per assignment. Results come back as files in a reports folder. My own notes land in a drop folder and get picked up on the next cycle. Git is the postal service and the filing cabinet at the same time: every memo is stamped, ordered and kept.

This started as a workaround and became the design. Chat as a transport failed for a boring reason: a conversation is not addressable. You cannot diff it, you cannot replay it, and you cannot prove afterwards what an agent was told. A file can do all three. An office that runs entirely on memos never has a meeting, and it never forgets one either.

The four-hour cycle, the ledger, and the off switch

Jenkins runs jobs on a schedule, and so does this. Every four hours a scheduled task runs a short script. The script checks for a stop file, pulls the repository, pipes the standing brief into Claude Code, and writes one line in a logbook. People imagine the orchestrator as a large system. It is a timer and a short script, and the intelligence it wakes is rented by the minute.

The run ledger is one text file. Every run appends exactly one line: the time, what it did, and why it stopped. Append-only, like a paper logbook filled in with a pen. Nothing is ever erased or rewritten, which is what makes it evidence rather than a status display. The ledger is also watched from outside: if its newest line gets too old, that silence raises an alarm on its own, because a fleet that has stopped writing might not be resting.

The off switch matches the rest of the design. It is a file. A file named PAUSE in the repository is the first thing every run checks, and if it exists, nothing runs. Stopping the entire fleet from anywhere in the world means creating one empty file.

Why a file and not a flag A stop switch has to work when the thing it stops is broken. A file in the repository needs no service to be up, no API to answer, and no credential to still be valid. It is checked before anything else happens, by the dumbest part of the system.

Is a worker alive, dead, or slow

A parallel fleet needs to answer one question every cycle: what happened to the workers I dispatched last time. The first version of that check got it wrong in both directions on the same day, which is how the real shape of the problem surfaced. One signal cannot separate three states, and there are three: never spawned, spawned and dead, and spawned and slow. Treating a slow worker as dead means respawning work that is already running. Treating a never-spawned lane as slow means waiting forever for something that never started.

The fix is a spawn record written at spawn time, plus a liveness checker that reads it. A lane with no spawn record was never started, so acting on it is a first attempt rather than a recovery. A lane with a spawn record and no report is either dead or slow, and the deadline in the record is what separates those two. The general lesson is the one this platform keeps relearning in different clothes: a check that cannot distinguish "did not run" from "ran and passed" is not a check.

The reviewer, and the ledger that stops it repeating itself

Codex runs against the repository under a written, read-only advisory contract. It reads, it reasons, and it reports. It does not write code, it does not merge, and it does not touch anything live. Its output is a verdict per branch, either LAND or FIX, with the reasons attached and the specific commit it judged named in the verdict, so a verdict cannot silently drift onto a different revision.

Every finding it produces goes into a findings ledger, which is the advisory channel's memory. Each finding gets one of three dispositions: CONFIRMED when I agree it is real, REJECTED with the reason recorded so it is not re-argued, or FILED when it became a tracked work item. The reviewer reads this ledger before every run and may not re-report anything already recorded. A rejected finding can be challenged once more, with new evidence, and then it stops.

Two details make the ledger honest rather than decorative. It records misses and partial hits, not only confirmations, because a ledger of nothing but hits teaches nobody how much to trust the channel. And a deferred finding is written as confirmed and deprioritised, never quietly moved to rejected, so the list of things I know about and have not done stays visible.

The loop, working: a real security defect, start to finish

Here is the whole review loop on one actual defect from the outage week, because the mechanism is only worth anything if it catches something.

Before any file gets written by an agent, a pre-write hook scans the content with the gitleaks rule set and blocks anything that looks like a secret. Like gitleaks itself, it reads an allowlist from a .gitleaks.toml file for the handful of strings that only look like secrets, a public signing key being the usual example. The allowlist is what stops the guard being so noisy that someone switches it off.

  1. Claude finds a gap. An evaluation suite written to attack the platform's own guards flags the allowlist loader as suspect.
  2. Codex confirms it, and it is worse than the flag. The loader pulled its allowlist out of the config with a non-greedy pattern that stopped at the first closing bracket inside a regular expression. Three of the eight suppressions were loading. The other five were silently absent, so the guard's behaviour did not match its own written configuration.
  3. Claude fixes it. Parse the configuration with a real TOML parser instead of a pattern match, and compile the allowlist from the parsed array.
  4. Codex catches a defect in the fix. The new parser did not handle every way the config file could be malformed, and some of those paths could have widened what the guard let through.
  5. Claude fixes that, and Codex returns LAND. Absent, unreadable, garbled and wrong-typed configuration all now yield an empty allowlist, individual malformed entries are skipped without discarding their valid siblings, and the exception for private keys holds even for allowlisted paths.

Five alternating steps across two vendors, with no stage where a model graded its own work, all against a repository that was frozen because the platform was down. The verdict that closed it also recorded one thing it did not do: an unreadable-configuration path is implemented but not directly exercised by a test. That is written down as a coverage gap rather than rounded up to done, which is the habit this whole page is really about.

The week it refused to act

On 2026-08-04 the platform went dark, and the fleet's most important behaviour is what it did next, which was nothing. The scheduled cycle that ran at 18:35:15 that evening completed normally and dispatched four workers. Forty minutes later the platform was gone. What caused that is still unknown and the write-up says so.

Every scheduled cycle after that woke up on time, tried to pull the repository, failed to resolve the git server, checked public DNS and found it healthy, concluded that the internet was fine and the lab was not, and declined to dispatch anything against a repository state it could not confirm. Each one wrote its reason into the ledger and exited. That repeated for the entire outage with zero blind dispatches, and the ledger is where you can read it, one dated line per refusal.

What this does and does not prove It proves the dispatch discipline: an estate that stops cleanly when it cannot see. It does not prove that every guard around that discipline was sound. The same week's reviews found commit hooks that failed open rather than closed, and a ledger that could not push its own lines. Both became fixes, and they are named here rather than left out.

The outage also produced the most productive build window this platform has had, for an unglamorous reason: a frozen repository is a stable one. Nothing merged under anyone's feet for days, so branches could be built and reviewed against a tree that did not move.

The full account of the outage, including the two sections that cannot be written until the hardware is back, is a separate write-up.

Who merges, told straight

The fair challenge to any page like this is simple: so the fleet is merging its own work? Yes. Hundreds of pull requests so far, and saying that plainly matters more than the number, because the repository's own history would tell you anyway.

The line that keeps it honest is the difference between authority and execution. Merge authority is mine. Merge execution is delegated for a narrow, written class of routine change. A change lands on its own only when all of these hold at once: it is inside the written routine contract, continuous integration is green, the rival vendor returned a clean LAND verdict, the two vendors do not disagree, and no hook tripped. Anything consequential waits for me, and so does anything at all that raises a question. The test is not how big the change is. It is whether there is a doubt anywhere in the chain.

Today that boundary is written policy plus commit hooks, and the outage week's reviews found that some of those hooks failed open rather than closed. So the fence is discipline, and the work that turns it into architecture is in flight: a separate machine identity for the agents, a contract file that names the routine class, and branch protection that enforces the line instead of trusting behaviour. The contract file is itself out of contract, so the fleet can never widen its own permissions. One number here is still an estimate rather than a measurement: "hundreds" is my own figure, and the split between my merges and the fleet's is recoverable from the git history and gets counted before it is quoted as a count. The accepted risk register carries the same row, dated.

Everything that needs my hands ends up in one place, the operator queue. Today that queue is kept by hand, and the hand-kept version earns its keep: it ran through the outage week and the count of items waiting on me was driven to zero before recovery day. The generated version, a file rebuilt from the repository's own state every cycle, is designed and not built. The design holds four kinds of thing: merges held for my decision, rulings the fleet needs before it can proceed, hands-only work like hardware and credential ceremonies, and timed obligations like certificate renewals, with every item carrying its age, its source, and what it unblocks.

Two rules are what will make the generated queue trustworthy, and neither of them runs yet. Nothing will be checked off by hand: an item is to clear only when the next cycle observes the evidence, whether that is a pull request showing merged, an answer sitting in the drop folder, or a certificate date that changed. And it will not be allowed to rot in silence: an item that ages past its threshold is to push an alert out through the outside channel, which is itself a design. The prototype settled the idea. What is left to build is the clerk.

The automatic review loop is designed and gated

In the picture above, the review step happens because I run it. Making it automatic, so a cycle dispatches the reviewer itself with no paste in the middle, is designed and gated, in those words. The gate is a credential durability test. The reviewer's subscription credential is a file, and the command-line agent will accept one on standard input, which means it can reach a short-lived runner the same way every other secret in this platform does. What is not yet measured is whether that credential survives a refresh when the runner has nowhere to write the refreshed copy back to. Until that test returns, nothing is built.

The reason the gate exists at all is spend. The credential path keeps the reviewer on a flat subscription instead of metered per-token billing. If the durability test says the credential cannot survive in a short-lived runner, the honest options are a longer-lived host or metered billing, and that is a decision rather than an implementation detail. Building the loop first and discovering the cost afterwards is exactly the mistake this gate exists to prevent.

What is real today, and what is not

The rule this whole site runs on is that a design which has not run is a plan, and the page says so in those words. Applied here:

  • Running today: the timer-driven cycle, the file transport, the drop folder, the append-only run ledger, the PAUSE kill switch, the spawn-record roll call, the cross-vendor review with its findings ledger, the fleet's routine merging, incident analysis written by the fleet from primary sources rather than from my memory, and the refusal to act when it cannot verify. The outage proved the last one.
  • Run by hand today: dispatching the reviewer, the wave dispatch, and the operator queue itself.
  • Designed and not built: the written routine contract as a file, the separate machine identity, branch protection, the generated operator queue, the half-hour tick as a live trigger, the automatic review loop described above, the outside dead-man switch, and the three in the opening section: live incident triage, emergency work alongside me, and review of an architecture proposal before it is built.

One sentence for the whole page: the timer is dumb, the agents are careful, the files are the truth, and nothing that raises a question lands without me.
