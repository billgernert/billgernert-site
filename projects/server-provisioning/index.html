Technical project walkthrough

How I built one server provisioning workflow with two front doors

A Windows or Linux request becomes a running virtual machine with an allocated address, infrastructure state, operating-system configuration, Zabbix monitoring, DNS, and a committed host record. Windows servers also join Active Directory and enforce Duo MFA for remote desktop logins, with the Windows features and tools selected on the form already installed. Jenkins can coordinate the run, or Backstage can open a reviewed request that Gitea Actions applies without Jenkins. Both routes use the same repository scripts, Terraform definition, and Ansible playbooks.

Built from the current Jenkinsfiles, provisioning request schema, Backstage template, Gitea workflows, apply driver, Terraform configuration, Ansible playbooks, and the screenshots captured from the running interfaces.

At a glance

Outcome
A Linux or Windows request reaches a running, monitored server and a committed host record through either Jenkins or Backstage with Gitea Actions.
Operating scope
The live workflow coordinates address allocation, Terraform, Proxmox, Ansible, Vault, DNS, monitoring, and Active Directory for Windows.
Evidence
The Backstage route completed a measured run in 5 minutes 21 seconds on 2026-08-23. The page also carries captures from both request paths and their approval gates.
Primary lesson
Both front doors revalidate collisions, and post-creation failures retain enough state for the next run to continue forward safely.

The Windows form shows what the workflow can build

I started this walkthrough with Windows because the form makes the scope visible before the job runs. The request names the machine and its role, sets compute and storage, chooses a tagged Windows Server template, and can add tools, Windows features, a data disk, nested virtualization, and a published DNS record. The help text puts each constraint next to the choice that activates it.

The Windows Jenkinsfile has more stages than the Linux one because template resolution, WinRM, password generation, and disk movement are Windows-only. Some disk work is conditional. Moving the operating-system disk runs only for node-local storage, and adding a data disk runs only when one was requested.

The pipeline resolves a template by tags instead of storing a template number in code. Terraform clones it on shared storage, then the job expands or moves disks as requested. A first-boot script brings up WinRM over HTTPS. Ansible uses that channel to rotate the bootstrap password, rename and join the computer to Active Directory, install the monitoring agent, configure time and firewall rules, enforce Duo on remote desktop logins, install allowlisted tools and roles, and initialize the optional data disk. Reboots happen inside the playbook where Windows requires them.

A per-host administrator password and monitoring key are created during the run and stored in Vault. The values do not become Jenkins parameters or Git content. The job retrieves them only for the stage that needs them.

Linux uses the same backbone with fewer choices

Linux uses a shared cloud image, so it does not need the Windows template-resolution, WinRM, password-generation, or disk-movement stages. A configuration profile can add a CI runner after the base operating system is ready.

The short form is intentional. The role selects the allowed network, and the requested memory feeds the placement check. Terraform creates the VM and cloud-init sets the initial network and SSH access. Ansible waits for SSH, applies the base configuration, and installs the per-host monitoring key. The DNS and host-manifest stages are the same end of the story as Windows.

Jenkins is the coordinator in both versions. It renders parameters, starts an ephemeral provisioner pod in Kubernetes, checks gates, pauses for approval, keeps the stage log, and sends the result. It does not allocate an address, create a VM, configure an operating system, or invent credentials by itself. The systems below still own those operations.

Both Jenkins pipelines follow six phases

The stage lists are longer because Jenkins gives each operation its own log and failure boundary. At the workflow level, those stages fit into six phases.

One request becomes a recorded server

Phase 1DescribeValidate the name, role, size, operating system, storage, and optional features.
Phase 2Prove safeCheck network support and ask every inventory whether the name already exists.
Phase 3Reserve and planAllocate the address, select capacity, choose a template when needed, and build the Terraform plan.
Phase 4Approve and createReview the change, apply the saved plan, create the VM, and mark the creation boundary.
Phase 5Configure and connectRegister monitoring, configure the guest, join supporting services, and publish DNS.
Phase 6Record and recoverCommit the host manifest, report the result, and retain enough state for a safe rerun.

Cyan marks the ordered automated path. Amber arrows show the handoff from one phase to the next. Each phase ends with enough recorded state for the next phase to know what happened.

The approval gate shows what will change

Jenkins sends this email after Terraform has produced the plan and before the pipeline applies it. The message identifies the machine, allocated address, VM identifier, selected node, role, storage, and requested resources. The button opens the waiting Jenkins input step, where the operator can apply or abort. A plan that would replace an existing machine uses destructive wording so it cannot look like an ordinary new-server approval.

  1. Describe the machine. Jenkins validates its parameters before checkout-dependent checks run. Windows adds NetBIOS length and character rules, storage limits, and the requirement that Hyper-V includes nested virtualization. Values offered by the form are defined in version-controlled pipeline code.
  2. Prove the request is safe. The target check rejects a role whose network path is not supported. The collision checker asks address management, the hypervisor, monitoring, committed host manifests, and configuration inventory whether the name already exists. A confirmed match stops the build. An unavailable source is unknown, and unknown also stops the build. These checks run before a new address is reserved.
  3. Reserve capacity and produce a plan. NetBox reserves the next free address in the role’s allowed prefix. The job derives the gateway and VM identifier from that allocation, then selects an online hypervisor with enough free memory and disk. Terraform opens one workspace for the requested machine and stores its state in PostgreSQL. Vault supplies the provider and backend credentials at run time. Jenkins saves the plan that the approval step will review.
  4. Approve and create. Jenkins sends the request details and a link to a bounded approval gate. If Terraform says an existing machine would be replaced, the message and button use destructive wording. Approval applies the saved plan. Once the hypervisor has created the VM, the job records that boundary so later cleanup cannot release an address that a live machine still uses.
  5. Configure and connect the guest. Zabbix receives a host object and a newly generated per-host key. Vault keeps that key for the agent configuration. Linux is configured over SSH. Windows waits for repeated successful WinRM checks before Ansible starts because first boot can briefly open and close the port. Ansible handles the operating system; a DNS-specific step then creates the forward record and creates a reverse record only when the matching reverse zone exists.
  6. Write the durable record. The final stage creates a host manifest in Git with the selected node, address, sizing, role, and build reference. A later run reads that manifest and reuses the recorded node rather than accidentally planning a move.

Backstage provides the same workflow without Jenkins

Backstage is an internal developer portal. In this project it does not provision a machine directly. Its software template collects the request, validates the form shape, writes a small declarative request file, and opens a pull request. After that handoff, Gitea Actions performs the checks and the apply. A measured run on 2026-08-23 completed in 5 minutes 21 seconds without calling Jenkins or using a Jenkins agent.

The pull request is the first half of the control path

The request file is the contract between the portal and the automation. A Gitea workflow validates it against the schema, checks that the role maps to a supported target, and runs the same fail-closed collision checker used by Jenkins. It then runs Terraform against an empty local backend with placeholder placement values. That plan checks configuration and sizing without reading shared state or reserving an address.

The check job authenticates to Vault with a portal-specific AppRole. Its policy can read the credentials needed for validation, but the pre-merge job does not write infrastructure or lifecycle records. A reviewer gets a pull request containing the requested machine and the four check results. Merging that request is the approval.

The merge is the second half

A separate Gitea Actions workflow notices the newly added request on the main branch. It installs the provisioning toolchain in the runner and passes the file to the portal apply driver. That driver revalidates the request, repeats the target and collision checks, allocates the address, selects the node, runs Terraform, registers Zabbix, configures the guest with Ansible, registers DNS over WinRM, and writes the host manifest.

The driver calls the same scripts and playbooks as the Jenkinsfiles. The orchestration code is different because Gitea Actions has no Jenkins stages or input step, but address allocation, collision detection, placement, infrastructure definition, guest configuration, and registration remain shared. A manual Actions dispatch can rerun a named request when a previous apply needs to continue.

Jenkins route

  1. Jenkins renders the parameter form.
  2. The pipeline validates, checks, reserves, and plans.
  3. An operator approves inside the Jenkins run.
  4. The saved plan is applied from the provisioner pod.
  5. A Windows agent handles AD-integrated DNS.
  6. Jenkins keeps the stage log and notification.

Backstage and Gitea route

  1. Backstage writes a request and opens a pull request.
  2. Gitea Actions runs schema, target, collision, and plan checks.
  3. A reviewer approves by merging the pull request.
  4. A merge workflow applies through the shared driver.
  5. Ansible reaches AD-integrated DNS over WinRM.
  6. Gitea keeps the checks, apply log, and committed request.

The two routes share the systems that own the result. They differ in request, approval, orchestration, and log location. This is why the Backstage path can continue if Jenkins is unavailable without creating a second Terraform or Ansible implementation.

What the workflow touches and why

A provisioned server is not finished when the hypervisor reports that a VM exists. The workflow has to leave several systems describing the same machine. Each one has a narrow responsibility.

How it runs now

This workflow is event-driven. Nothing polls for a machine to build. A request starts the control path, and the creation boundary decides what recovery is safe.

WhenWhat runsWhat happens next
On requestJenkins validates its submitted parameters, or Backstage writes a request and opens a pull request. Target and collision checks run before infrastructure is changed.A rejected or unverifiable request stops before an address is reserved. A valid request continues to planning and review.
On approvalJenkins applies the saved Terraform plan after its input gate, or merging the Backstage request starts the Gitea Actions apply workflow.The workflow allocates or confirms the machine state, configures the guest, registers monitoring and DNS, and writes the host manifest.
On failure before creationThe unsuccessful handler checks the creation marker and calls the idempotent NetBox release path.The reserved address is released because no VM uses it. The request can start again as a clean build.
On failure after creationThe workflow keeps the VM, its address, Terraform workspace, and completed registrations. The failed stage remains visible in the run log.Cleanup does not dismantle a live machine. The next run continues forward from the recorded state.
On rerunThe safety checks run again. An approved reconcile reuses the existing address, live or manifested node, per-machine workspace, and idempotent registration steps.The workflow finishes the missing integration or configuration work and commits the host manifest when the full path succeeds.

What broke while I was building it

2026-07-14The collision gate checked the wrong NetBox objects

The first checker asked NetBox for devices and virtual machines. This pipeline records a provisioned host as an address with a DNS name, so the query could return clean for a name that was already allocated. The checker now reads address records and committed inventory as well as the hypervisor and monitoring system.

2026-07-14The checker failed, but the pipeline continued

The collision script originally piped its report through tee. The shell returned the status of tee, which was successful, instead of the checker’s nonzero status. Output redirection replaced the pipe, and the gate now refuses an unset or unparseable result. The target-reachability gate received the same fail-closed treatment.

2026-07-14An aborted approval leaked the reserved address

The release logic ran in the failure handler, but rejecting a Jenkins input marks the build aborted. The reservation remained in NetBox. Cleanup now covers unsuccessful outcomes and checks the creation marker before deciding whether an address can be released.

If I were recreating this

  1. Start with one request contract. Define the machine facts once, then make Jenkins parameters and the Backstage schema prove they offer the same choices.
  2. Make every ownership boundary explicit. Address management allocates addresses, Terraform owns infrastructure state, the hypervisor runs VMs, Ansible configures guests, monitoring owns the host check, DNS owns names, and Git keeps the durable record.
  3. Run safety checks before allocation. Validate the target and check the requested name everywhere it could already exist. Treat an unreachable source as unknown and stop.
  4. Record the creation boundary. Cleanup rules must know whether an address is only a reservation or already belongs to a live VM.
  5. Keep the implementation below the orchestrator. Put provider calls in scripts, infrastructure in Terraform, and guest configuration in Ansible. A second front door can then reuse them without copying the Jenkinsfile.
  6. Test the rerun path. A useful provisioning workflow can resume after the VM exists. It retains the address and recorded placement, repeats idempotent integrations, and writes the manifest when the remaining work succeeds.
