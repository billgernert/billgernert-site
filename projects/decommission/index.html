Project story

Decommission, with the gate that says no

A destroy path is only useful when it can prove it is destroying the thing you asked for. This one stops if the plan is empty, tears the stack down in the safe order, and keeps the one credential a restored machine still needs later.

The key guard is against false success

The dangerous decommission is not the obviously broken one. It is the one that reports success after touching nothing. An empty destroy plan looks clean in an email and leaves the machine right where it was, which is why this path treats "nothing to destroy" as a stop condition rather than a green exit.

That gate sits in front of the rest of the teardown because the rest of the teardown is real. Once the pipeline starts releasing addresses, removing monitoring, and deleting state, the machine needs to be on an actual destruction path instead of on a polite no-op.

The teardown order is deliberate

The machine is torn down in the reverse order the provisioning story created it. The VM has to be genuinely gone before its IP address goes back to the pool, or the pool starts shrinking in a way the next build only discovers later. Monitoring is cleaned up as part of the same path, so a retired machine does not keep reporting as a live one by accident.

This is the same design rule as provisioning. The repository path tells the truth about the world only if destroy steps are as explicit as create steps.

The useful lesson came from restore, not destroy

The credential I deliberately keep is the per-host local-admin password. Early on I removed it when a machine was decommissioned, then restored a VM from backup and could not log in because the machine came back but the one secret tied to that machine did not. The decommission path now keeps that password in Vault so a restored VM is still reachable.

That is the kind of edge case only shows up when the decommission path and the recovery path are both real. The fix is small, but it is the difference between "destroyed cleanly" and "restored usefully."
