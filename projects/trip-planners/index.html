Building and hosting the London and Paris planners

I wanted a trip plan I could change one decision at a time, with meals, places to visit, and a map of each day. Building the planners gave me applications to run on AutomationLab, move to Cloudflare, and use to develop the platform's shared deployment path.

How to use a planner

  1. Set your first and last day, then choose a hotel. The map starts there.
  2. Choose neighborhoods for a day, then select meals and activities. A selection collapses the other choices. Use Change to compare them again, or Use suggested day to start with a set of stops.
  3. Open Map for this day to see the order of your stops. Open the full day to add places of your own. Direction links show the street route.
  4. Copy or print the itinerary when you want to take it with you. Check venue hours and bookings before travelling.

There is no login or shared data. Each city's plan stays in this browser, and clearing site storage removes it. Choosing a hotel or activity here does not make a reservation.

They began with decisions for an actual trip

I brought the places I was considering into a React and TypeScript interface so I could compare them within a day. London and Paris share the same application, with separate city data for venues, neighborhoods, and travel information. Vite builds the interface into files a web server can serve.

The planner's behavior follows that use: choose a meal or attraction, collapse the alternatives, then see the saved stops on the day's map. Neighborhood choices narrow the places offered nearby. I can reopen a choice without rebuilding the itinerary.

I ran the apps on AutomationLab in containers. Nginx serves the interface, and a small API stores the shared itinerary on persistent storage in Kubernetes. That lets a saved choice appear in another signed-in browser. Getting the apps running exposed the hosting work around the interface: building it, keeping its state, assigning a hostname, and protecting access.

Moving the private apps to Cloudflare

I adapted the static builds for Cloudflare Pages and moved shared itinerary storage to D1, Cloudflare's managed database. A Worker handles the API requests between the browser and D1. Cloudflare Access uses Microsoft Entra sign-in to protect the private apps.

Development and production have separate hostnames and databases. I test changes in development before promoting them. The Kubernetes copies remain independent in the lab, which gives me an application to work with as I change the platform's deployment process.

What the planners contribute to the paved road

Deploying another app should not require repeating the hosting decisions I made for these planners. I am using the lab copies to develop a shared deployment definition for a static interface with saved state, a hostname, and sign-in protection. That supported path is the paved road, also called a golden path.

The shared deployment project is still in progress. Access configuration through reviewed changes and a portal template that opens a pull request for a new web app are subsequent steps. The planners give that work a concrete application to support, including a browser interface and data that has to survive a deployment.

The previews on this page have a separate purpose: let visitors use the interface without access to a private trip. Their state stays in the browser. They publish with the portfolio site's existing checks and publishing pipeline, so they are not evidence that the new deployment path is complete.
