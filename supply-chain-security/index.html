Software supply chain

Checking the code and containers before they run

Most of what runs in the lab is built from other people's code and packaged into containers. So before anything ships, it gets scanned for leaked secrets and known bugs, signed if it passes, and refused at the door if it is not signed. Two of those checks looked like they worked and did not. This page walks the pipeline and the two lessons that made it honest.

The problem in one sentence

You did not write most of the code you run. A container image is your handful of files sitting on top of a base image, a language runtime, and dozens of libraries, all pulled from the internet. Supply chain security is the work of knowing what is in that stack, checking it for known problems, and proving that the thing you tested is the exact thing that runs. If you skip that, a bug in a library you have never heard of is now your bug.

Scan: secrets and known bugs, on every change

Two scans run before code can merge. The first looks for secrets, an API key or password accidentally committed, and blocks the merge if it finds one. It runs as a pre-commit check and again in the pipeline, so a developer who skips the local hook still gets caught. The second scan reads the code, the infrastructure definitions, and the built container image, and reports known vulnerabilities in any library or base image they pull in. Both run on every pull request, not on a schedule, so a problem is caught while the change is small and fresh in someone's head.

Sign: prove this exact build passed

A build that passes the scans gets signed. The signature is a small cryptographic stamp that says "this specific image, byte for byte, is the one that passed." Alongside it the pipeline records a list of everything that went into the image, a kind of ingredients label for software. That label is itself signed and attached to the image, so later you can ask "what libraries were in the thing we shipped in March" and get a real answer instead of a guess. The signing key never sits in the CI system. It lives in the secrets server and the pipeline borrows it for the moment it signs, then gives it back.

Verify: refuse to run what is not signed

Signing is only worth something if something checks the signature. When the cluster is asked to run an image, a policy checks that the image carries a valid signature from the lab's own key before it is allowed to start. No signature, or a signature from the wrong key, and the image does not run. The check fails closed: if the verification service cannot make a decision, the answer is no, not "let it through and hope." That policy starts in audit mode, where it records what it would have blocked without blocking it yet, so you can see the real impact before you turn on enforcement and lock yourself out of your own cluster.

Provenance: where did this come from

Provenance is the paper trail: which pipeline built this image, from which commit, at what time. The signed ingredients label plus the build record let you trace a running container all the way back to the line of code and the pull request that produced it. That is the difference between "we think this is fine" and "here is exactly what it is and here is how it got here."

The weekly scan that hid fresh problems

The registry, where built images are stored, was scanned once a week. That felt thorough and it was quietly wrong. A build that happened on Wednesday would not be scanned until the next weekly sweep, so a serious vulnerability introduced mid-week was invisible for days even though the tools could see it the moment the image was built. The scan and the build were running on two different clocks. The fix was to scan at build time, when the image is created, so a fresh critical is caught immediately instead of waiting for a calendar to come around. A scan is only as current as its slowest clock.

A no-fix finding is a decision, not an ignore file

Some vulnerabilities have no fix available yet, and some do not apply to how you actually use the library. The tempting move is to add them to an ignore list and never look again. The problem is that an ignore list nobody reads becomes a place where real risk goes to hide. So an accepted finding is treated as a documented decision with an owner and a reason, reviewed rather than buried. The goal is not zero findings. The goal is that every finding was either fixed or consciously accepted by a named person who can say why.

What this adds up to

Scan on every change so problems are caught small. Sign what passes so the tested thing and the running thing are provably the same. Verify at startup so unsigned images never run. Keep the signing key in the secrets server, not in CI. And treat both the scan schedule and the accept list as places where a check can quietly stop checking, because those are exactly where the last two real gaps were.
